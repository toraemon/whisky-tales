# 📁 Backend フォルダ構成（WhiskyTales）

このドキュメントでは、WhiskyTales のバックエンドにおけるディレクトリ構成と、その設計意図を記録しています。

---

## 📂 フォルダ構成

```plaintext
src/
├── controllers/     // HTTPリクエストの受け口（req/res処理、usecaseの呼び出し）
├── routes/          // Expressのルーティング設定
├── usecases/        // アプリケーションサービス層（トランザクション制御、複数logic/repoをまとめる）
├── logics/          // 業務ロジック（ドメイン知識、条件分岐など再利用可能な処理）
├── repositories/    // DB操作層（Prisma等を使ったCRUD処理）
├── schemas/         // Zod等のバリデーション・DTO定義
├── middlewares/     // 認証・ロギング・エラーハンドリング等のミドルウェア群
├── config/          // DB接続・環境変数などの設定
├── utils/           // 汎用ユーティリティ関数
```

---

## ✅ ディレクトリ分割の目的

| 層 | 目的・役割 |
| --- | ---- |
| controllers | HTTPレイヤー。リクエストを受け取り、適切なユースケースに処理を委譲する |
| usecases | アプリケーションサービス層。ビジネスフロー全体を担当し、トランザクション管理もここで行う |
| logics | 業務ルールに基づく関数群。再利用性・テスト性を考慮してユースケースから分離 |
| repositories | DBアクセス層。Prismaを使って純粋な永続化処理を記述する |
| schemas | 入出力のバリデーション、APIレスポンスの型定義などを担当 |
| middlewares | ログ出力、例外処理、認証処理などの横断的な関心事をここに集約 |
| config | 環境や外部設定に関するものを管理 |
| utils | プロジェクト共通で使える小規模な関数群を格納 |

---

## 💬 検討と決定の経緯

### 🔍 検討した内容
- 現在の業務にて usecases（旧：services）層が肥大化し、関数の責務が不明瞭になるという課題があった。
- トランザクション管理とビジネスロジックを分離することで、それぞれの関心ごとを明確にしたいというニーズがあった。
- 再利用可能なドメイン知識を logics に分けることで、保守性・テスト性を向上させる。

### ✅ 決定理由
- usecases にトランザクション制御とフローを集中させることで、処理の起点が明確になる。
- logics を用意することで、条件判断・計算・再利用関数などを切り出し、責務を明確にできる。
- 現時点では DDD や Aggregate まで導入する規模ではないため、シンプルかつ実用的な分離を優先。
